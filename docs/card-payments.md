# Mercado Pago embedded cards

New deposits use Checkout Transparente through the official MercadoPago.js v2 Card Payment Brick inside the cashier. The form uses the site theme and offers credit/debit methods available to the merchant in Brazil, in one installment. Availability and approval depend on Mercado Pago and the issuing bank; this is not a standalone card-validity checking service.

The ignored `.env.mercadopago` supplies `MERCADOPAGO_ACCESS_TOKEN` and `MERCADOPAGO_PUBLIC_KEY` from the same application. The deploy carries both to the backend. Only the public key is returned to the authenticated player. No frontend build-time credential is required. Other applications and their webhook registrations are unchanged.

`POST /api/deposit/card` prepares a durable deposit without creating a provider charge. Mercado Pago collects/tokenizes PAN and CVV inside its secure fields; our server accepts only the resulting token and a restricted payer/method payload through `POST /api/deposit/card/pay`. PAN/CVV fields are refused. Tokens, payer documents and email are neither persisted in the card receipt nor browser recovery storage. The backend takes the amount and reference from its durable receipt, checks that the selected provider method is a card, enforces one installment, and creates a payment with a stable provider idempotency key. A request digest survives ambiguous timeouts; a different token/body cannot silently reuse an attempted deposit. After an uncertain result, verify the existing payment before initiating another deposit.

The backend validates every payment against production mode, card type, exact BRL amount, external reference and deposit metadata. Credit and receipt acknowledgement share the wallet transaction. Pending, declined and bank-challenge states never credit the wallet. Status recovery fetches provider records; browser success messages alone cannot credit. The cashier polls pending payments while open and also offers explicit verification. Test player accounts cannot create live charges.

3DS is enabled in optional mode. When required by the bank, a Status Screen Brick presents the issuer challenge within the cashier. Its result still needs backend verification before wallet credit. Closing the cashier unmounts the secure fields; refreshing restores only the deposit reference and obtains payment/challenge state from the server. Browser storage never retains the card token or challenge payload.

Existing Checkout Pro deposits remain recoverable through their original hosted link and provider verification. No new hosted preference is created by the current route. Refunds and chargebacks after wallet credit require merchant reconciliation; automatic spent-wallet reversals and background webhook settlement are not implemented. Additional payments against one deposit never create another wallet credit.

Official references: [Card Payment Brick](https://www.mercadopago.com.br/developers/en/docs/checkout-bricks/card-payment-brick/default-rendering), [payment submission](https://www.mercadopago.com.br/developers/en/docs/checkout-bricks/card-payment-brick/payment-submission), [3DS](https://www.mercadopago.com.br/developers/en/docs/checkout-bricks/how-tos/integrate-3ds).
